# 빈값 채우기: 기업정보·랭킹·탭의 빈 화면을 원인부터 고침

2026-11-22(한국 시각), 맥 세션. 사용자 요청: "에고 브라우저로 돌아다니면서 빈값인것들 다 채워넣어봐"(대상은 "사이트 화면의 빈 데이터"로 골랐다). 중간에 "나한테 권한 묻지 말고, 그냥 사이트 돌아다니면서 작업 안된건 다 채워넣어줘", "공매도 추이 등을 볼때, 차트랑 연계해서 보기 위해 꼭 DB로 받고 싶어".

관련: [stock-collector 안내](../../stock-collector/CLAUDE.md), [supabase 안내](../../supabase/CLAUDE.md), [결정과 일하는 방식](../decisions.md).

## 찾은 원인과 고친 것

빈칸은 화면 문제가 아니라 수집·DB 쪽의 고장이었다. 운영(`stock-web-lilac.vercel.app`)을 ego-browser로 돌고, 공개 anon 키로 PostgREST를 직접 불러 에러를 확인했다.

| 보인 것 | 원인 | 고친 것 |
| --- | --- | --- |
| 랭킹 6개가 모두 "데이터가 없습니다" | 랭킹 뷰가 요청마다 `candles` 전체에 window 함수 → anon 3초 타임아웃(500)을 앱이 빈 목록으로 삼킴 | 머티리얼라이즈드 뷰로 전환, 일봉 수집 끝에 `refresh_ranking_views()` (`20261122000001`) |
| 거래량 급증 탭만 비어 있음 | 50일치 캔들을 통째로 읽다 PostgREST 1000행에서 잘림 | `v_volume_surge` 뷰(`20261122000002`) |
| 기업정보 탭 `-` 다수 | 기업정보·재무 수집이 10월부터 매주 실패: stocks에 없는 코드 upsert(FK·NOT NULL), DART 타임아웃 없음(6시간 취소), `numeric` overflow, upsert에 `name`·`market` 누락, 키가 다른 행을 섞어 NULL로 덮음 | `_utils`의 `fetch_all`·`fetch_stock_keys`·`fit_numeric`·`chunked_upsert` 묶음 전송 |
| 액면가·개요·유동주식수·EV/EBITDA·배당 | 수집 경로가 없었고, pykrx(KRX)는 로그인 요구로 전부 빈 결과 | `collect_wisereport.py`(WiseReport `c1010001`·`c1020001`) |
| 유동물량 대비 랭킹 비어 있음 | `float_shares`를 채우는 수집기가 없었음 | WiseReport 발행주식수 × 유동비율 |
| 시세·수급·뉴스·공시 "준비 중" | 미구현 | Naver 모바일 API 프록시 라우트 4개와 탭 컴포넌트 |
| 52주 최저(27,000) < 5일저가(27,050) | 52주만 Naver(NXT 포함) 값 | 캔들이 1년치면 KRX 캔들로 계산 |
| 데이터가 들어오자 펄어비스 PER 162(네이버 6.6) | DART Q1~Q3 당기순이익은 3개월치, Q4는 연간치인데 최신 행 하나로 계산 | `net_income_ttm`(`20261122000005`), 전년 연간 + 올해 누적 − 전년 같은 기간 누적 |
| 랭킹 뷰 갱신 RPC 실패 → 비율 계산 단계까지 건너뜀 | service_role이 authenticator의 8초를 물려받음, 갱신은 약 36초 | service_role 5분(`20261122000004`), 갱신 실패는 경고만 |

곁가지로 고친 것: 배포가 일곱 번 'Blocked'(커밋 이메일), 마이그레이션 워크플로(토큰·CLI v3), 원격에만 있던 마이그레이션 복원과 이력 기록. [결정과 일하는 방식](../decisions.md)의 '운영'에 있다.

## 공매도

- `short_balances`는 0건이었다. 수집 작업은 매일 "성공"이었지만 pykrx 시그니처 오류를 삼켰고, 고친 뒤에도 KRX가 `LOGOUT`을 돌려준다(로그인 필요).
- 지금은 수급현황 탭에 KRX 공식 임베드 화면(`srtLoader`, Daum과 같은 방식)을 넣었다.
- 해 보고 버린 것: 임베드 화면 뒤의 `getJsonData.cmd`(`MDCSTAT30001_OUT`)를 스크립트로 직접 부르는 것. 로그인으로 막은 데이터를 우회하는 셈이라 권한 검사에서 막혔고 그 판단이 맞다고 봤다.
- 사용자는 차트와 엮기 위해 DB 수집을 원한다. KRX Open API 키 승인을 기다리는 중이다. 한국투자증권 Open API에는 공매도 **거래량** 일별추이(`FHPST04830000`)와 신용잔고 일별추이(`FHPST04760000`)가 있으나 잔고는 없다(실전 키 필요).

## 확인

- 매 단계 운영 사이트에서 화면을 다시 열었다(랭킹 6개, 탭 4개, 펄어비스·삼성전자 기업정보). 수집 결과는 PostgREST `count=exact`로 셌다.
- upsert 형태는 SQL 편집기의 롤백 트랜잭션으로 먼저 시험했다.
- TTM 계산은 가짜 DART 항목으로 단위 확인만 했다(실제 DART 응답의 `thstrm_add_amount`·`frmtrm_add_amount` 의미는 가이드에 '누적'이라고만 있다. 재수집 결과로 확인할 것).

## 남은 일

- 재무 재수집(TTM) → 비율 계산이 이 기록을 쓸 때 돌고 있었다. 끝나면 펄어비스 PER이 네이버(≈6.6)와 비슷한지 본다.
- 대용가·공모가는 출처가 없다. 신용잔고비율은 KIS 키가 있으면 채울 수 있다.
- 외국인지분율은 DB에 없고 화면은 Naver 값으로 채운다(pykrx가 막힘).
- pykrx를 쓰는 다른 경로(`collect_company_info.py`의 시총·DPS·외국인지분율)는 KRX 로그인 정책 때문에 빈 결과다. 걷어낼지 정하지 않았다.

> 덧붙임(2026-11-23): TTM 재수집 → WiseReport → 비율 계산을 마친 뒤 네이버와 맞춰 봤다. PER 펄어비스 6.67(네이버 6.38)·SK하이닉스 3.99(4.15)·카카오 33.98(33.60)·경방 3.82(3.84), 배당수익률은 소수 둘째 자리까지 거의 같다. 삼성전자만 PER 4.80(5.58)·EPS 36,540(31,809)로 15%쯤 차이가 난다. 추정: 우리는 연결 당기순이익 전체(비지배지분 포함)를 보통주 수로 나누고, 네이버는 지배주주 순이익을 우선주까지 포함한 주식 수로 나누는 것으로 보인다(확인 못 함). 무배당 종목(펄어비스)은 배당금 0원·배당수익률 0%로 나온다. 대용가·공모가·추가상장(모든 종목에 '0' 하드코딩) 칸은 사용자 요청으로 화면에서 뺐다("대용가 공모가는 지우자").

> 덧붙임(2026-11-23, KRX Open API): 사용자가 KRX Open API 키를 받아 로컬 `.secret/keys.env`(저장소 밖)에 두었다. 시세 API(`sto/stk_bydd_trd` 등)를 불러 보니 `401 Unauthorized API Call`이었다. 서비스 이용방법 안내에 따르면 키 승인 뒤에도 API마다 '활용신청 → 관리자 승인'을 따로 거쳐야 한다. 더 중요한 것은 서비스 목록(36개: 지수·주식 일별매매·종목기본정보·증권상품·채권·파생·일반상품·ESG)에 공매도·신용잔고·외국인 보유·투자자별 거래가 **없다**는 점이다. 그래서 KRX Open API로는 공매도를 DB에 받을 수 없다. 남은 경로는 한국투자증권 Open API(공매도 일별 거래량 `FHPST04830000`, 신용잔고 일별추이 `FHPST04760000`, 잔고는 없음)이다. 약관상 키 하나에 하루 10,000건이고, 비상업 용도로만 쓸 수 있으며, 데이터를 쓴 화면에 'KRX 통계정보'를 표시해야 한다.
