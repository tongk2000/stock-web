# 5. 내 컴퓨터에서 실행하고 문제를 찾기

[목차](README.md) · [이전](04-data-flows.md) · [다음: 작은 수정 실습](06-practice.md)

## 먼저 알아둘 것

이 앱에는 샘플 데이터만으로 작동하는 독립 데모 모드가 없습니다. Node.js뿐 아니라 연결할 Supabase 프로젝트와 테이블·데이터가 필요합니다. 기존 개발용 Supabase를 연결할 수 있다면 먼저 그것을 사용하세요. 새 DB를 만드는 일은 화면 실행과 별도 준비입니다.

아래 명령은 Ghostty의 zsh에서 그대로 입력합니다. 맨 앞에 `!`를 붙이지 않습니다. 여러 창을 사용할 경우 명령을 실행하는 창의 현재 폴더를 확인하세요.

## 1단계: 실제 앱 폴더로 이동

이 작업 공간에서는 다음과 같습니다. 폴더를 옮겼다면 그 위치에 맞게 바꿉니다.

```sh
cd /Users/kdh/workspace/my/stock-web/source/stock-web
pwd
node --version
npm --version
```

`pwd` 결과 끝이 `source/stock-web`이어야 합니다. 그 안에 `package.json`이 있습니다. 바깥 `stock-web` 폴더에서 실행하면 npm이 프로젝트를 찾지 못합니다.

`node: command not found`이면 Node.js 설치부터 필요합니다. 현재 lock 파일에 기록된 Next.js의 요구 조건은 **Node.js 20.9.0 이상**입니다. 이는 최소 조건이며 특정 버전의 현재 지원 상태를 뜻하지 않습니다.

## 2단계: 필요한 도구 설치

```sh
npm ci
```

`package-lock.json`에 기록된 조합으로 의존성을 설치합니다. `node_modules`를 다시 구성하며 화면 코드나 DB를 초기화하는 명령은 아닙니다. 라이브러리를 새로 추가하는 작업에는 보통 `npm install 패키지명`을 쓰지만, 처음 실행하기 위해 의존성을 임의로 바꿀 필요는 없습니다.

## 3단계: 연결 정보 설정

**환경 변수**는 코드에 직접 적지 않고 따로 전달하는 주소·키·설정입니다. `.env.local`이 없다면 한 번 생성합니다. 아래 명령은 기존 파일을 덮어쓰지 않습니다.

```sh
if [[ ! -f .env.local ]]; then
  cp .env.example .env.local
fi
```

편집기로 `.env.local`을 열고 최소한 아래 세 값을 채웁니다. `여기에_...`는 설명용 자리이므로 그대로 사용하지 않습니다.

```dotenv
NEXT_PUBLIC_SITE_URL=http://localhost:3000
NEXT_PUBLIC_SUPABASE_URL=여기에_Supabase_프로젝트_URL
NEXT_PUBLIC_SUPABASE_ANON_KEY=여기에_같은_프로젝트의_anon_키
```

사이트 URL은 빈 문자열로 두지 마세요. `layout.tsx`에서 URL 객체를 만들 때 오류가 날 수 있습니다. 환경 변수를 바꾸었으면 개발 서버를 종료하고 다시 켭니다.

| 변수 | 실제 사용처와 필요 여부 |
|---|---|
| `NEXT_PUBLIC_SITE_URL` | 검색엔진용 절대 주소 등. 로컬에서는 `http://localhost:3000` |
| `NEXT_PUBLIC_SUPABASE_URL` | 웹의 서버·브라우저 Supabase 연결에 필요 |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 웹의 공개 연결 키. 사용자 세션과 RLS로 실제 접근을 통제 |
| `SUPABASE_SERVICE_ROLE_KEY` | Python 수집에서 사용. 현재 웹 `src`의 일반 조회에는 쓰지 않음 |
| `SUPABASE_URL` | Python 수집용 이름. 웹의 `NEXT_PUBLIC_SUPABASE_URL`과 이름이 다름 |
| `DART_API_KEY` | 재무·기업정보 수집에 사용. 웹 `.env.example`에는 없음 |
| `KIS_APP_KEY`, `KIS_APP_SECRET` | 예제에 있지만 현재 `src`에서 사용하는 코드가 확인되지 않음 |
| `STRIPE_*`, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` | 예제에 있지만 결제 구현으로 연결되어 있지 않음 |

`NEXT_PUBLIC_`은 브라우저에 전달할 수 있는 설정입니다. 관리자 권한인 service role 키를 이 접두사로 만들거나 화면 코드에 넣으면 안 됩니다. `.env.local`은 Git 제외 대상입니다. AI에게 문제를 설명할 때도 키 값 대신 **변수 이름과 오류 메시지**를 전달하세요.

## 4단계: 서버 실행

```sh
npm run dev
```

터미널에 준비 완료와 주소가 나오면 브라우저에서 `http://localhost:3000`을 엽니다. 3000번을 다른 프로그램이 사용하면 터미널에 다른 포트가 표시될 수 있습니다. 실제 표시된 주소를 확인하세요. 로그인 복귀 주소도 포트의 영향을 받습니다.

이 터미널은 서버가 실행 중인 자리입니다. 멈춘 것이 아닙니다. 종료는 `Ctrl+C`입니다. 다른 명령은 Ghostty/tmux의 다른 패널에서 실행하면 됩니다.

화면을 열어 다음을 확인합니다.

1. 홈 제목과 메뉴가 보이는가? 관심 종목이 없으면 비어 있는 안내가 나올 수 있습니다.
2. DB에 있는 종목 이름으로 검색되는가?
3. 종목 상세의 과거 차트와 기업정보가 보이는가? 데이터가 없으면 비어 있을 수 있습니다.
4. 별을 누르고 홈으로 갔을 때 관심 종목이 보이는가?
5. 로그인을 설정한 환경이면 로그인·닉네임·원래 페이지 복귀가 되는가?

## DB가 완전히 새 것이라면

웹의 환경 변수만 입력한다고 테이블과 종목이 생기지는 않습니다. 준비 순서는 다음과 같습니다.

```text
Supabase 프로젝트 준비
  → migrations 순서대로 적용: 표·권한·함수·view 생성
  → 수집 실행: 종목과 과거 주가 채우기
  → Google 로그인 및 허용 복귀 URL 설정
  → 웹 환경 변수 연결
  → 화면·저장·로그인 확인
```

**마이그레이션**은 DB 구조를 바꾸는 SQL 변경 기록입니다. 폴더에 파일이 있는 것과 원격 DB에 적용된 것은 다릅니다. 기존 파일을 마음대로 다시 실행하거나 삭제하지 말고 적용 이력을 확인합니다.

이 저장소의 [자동 적용 workflow](../.github/workflows/apply_migrations.yml)는 `main`에 `supabase/migrations/**` 변경이 push되면 DB 적용을 시도합니다. 따라서 SQL 파일을 수정해 올리는 일은 실제 원격 DB 변경으로 이어질 수 있습니다.

수동 적용도 가능하지만 연결할 프로젝트와 현재 적용 이력을 확인한 뒤 하는 별도 작업입니다. `supabase db push`는 화면 미리보기 명령이 아닙니다. 이 문서를 읽는 데 필요해서 운영 DB에 실행할 이유는 없습니다.

## 개발, 빌드, 배포의 차이

| 명령/작업 | 하는 일 | 이것만으로 하지 않는 일 |
|---|---|---|
| `npm run dev` | 수정하며 보는 개발 서버 실행 | 외부에 사이트 배포 |
| `npm run lint` | ESLint 코드 규칙 검사 | 화면·로그인·DB 정상 작동 보장 |
| `npm run build` | 배포용 결과물 생성, 타입·빌드 문제 확인 | 배포 서비스에 업로드 |
| `npm run start` | 만들어진 배포용 결과물 실행 | 먼저 빌드하지 않은 앱 빌드 |
| 호스팅 배포 | 서버에서 사이트를 제공하도록 등록·실행 | DB 수집 성공이나 Google 설정 자동 보장 |

`package.json`에 자동 테스트용 `test` 명령은 없습니다. `npm run build`만으로 사용자 기능 전체를 검사할 수는 없습니다. 빌드 때 환경 변수, DB 접근 또는 Google 폰트 다운로드 같은 외부 조건이 영향을 줄 수 있습니다.

현재 소스만으로 실제 배포 서비스·주소를 확정할 수 없습니다. 배포를 진행할 때는 앱 루트가 이 작업 공간의 `source/stock-web`에 있다는 점, 배포 환경 변수, 로그인 복귀 주소를 함께 확인해야 합니다. GitHub 저장소 자체의 루트는 로컬 바깥 작업 공간과 다를 수 있습니다.

## 자동 수집 예약표

다음은 [.github/workflows](../.github/workflows)에 적힌 예약입니다. 한국 시간으로 환산했습니다. 실행 성공이나 정시 완료를 확인한 기록은 아닙니다.

| 작업 | 예약 | 실행 파일 | 저장 결과 |
|---|---|---|---|
| 일봉 수집 | 평일 16:00 | `collect_candles.py` | `stocks`, `candles` |
| 재무비율 계산 | 일봉 수집 단계 성공 뒤 | `calculate_ratios.py` | `financials`의 비율 등 |
| 기업정보 | 월요일 09:00 | `collect_company_info.py` | 종목 정보·일부 재무 정보 |
| 재무정보 | 월요일 10:00 | `collect_financials.py` | `financials` |
| 공매도 잔고 | 평일 18:10, 재시도 20:00 | `collect_short_balances.py` | `short_balances` |

**cron**은 요일·시간을 쓰는 예약 표현입니다. **배치**는 자료를 한 번에 모아서 처리하는 작업입니다. 화면을 열어 놓아야 실행되는 작업이 아닙니다.

GitHub 저장소의 Actions에서 작업을 선택해 최근 실행과 각 단계 로그를 확인합니다. 코드에는 수동 실행도 정의되어 있습니다. 수집 작업은 DB에 쓰므로 새 자료가 필요한 대상 프로젝트를 확인한 뒤 실행합니다. Secrets는 자동 실행기에 전달하는 비공개 환경 변수 저장소입니다.

수집에는 `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, 작업에 따라 `DART_API_KEY`가 필요합니다. 자동 마이그레이션에는 `SUPABASE_ACCESS_TOKEN`과 프로젝트 식별 정보(`SUPABASE_PROJECT_REF` 또는 URL에서 추출한 값)를 사용합니다. 로컬 `.env.local`을 채웠다고 GitHub Secrets나 배포 환경 변수가 함께 채워지지는 않습니다.

Python을 로컬에서 실행하려면 웹 설치와 별도로 Python 환경 및 `stock-collector/requirements.txt` 의존성이 필요합니다. 공용 코드가 `load_dotenv()`로 `.env`를 읽으므로 수집용 `stock-collector/.env`를 사용할 수 있습니다. 웹용 `.env.local`을 자동으로 대신 읽는다고 가정하지 마세요. 일상적인 화면 수정에는 Python 실행이 필요하지 않습니다.

## 문제가 나면 어디부터 볼까?

| 증상 | 먼저 확인할 것 |
|---|---|
| `package.json`을 못 찾음 | `pwd`가 실제 앱 폴더인지 |
| 사이트가 연결되지 않음 | 개발 서버가 켜져 있는지, 터미널의 실제 주소·포트 |
| Supabase URL/key 오류 | `.env.local` 이름·값, URL과 키가 같은 프로젝트 것인지, 서버 재시작 |
| `Invalid URL` | `NEXT_PUBLIC_SITE_URL`이 비었거나 주소 형식이 잘못됐는지 |
| 종목을 찾을 수 없음 | `stocks` 데이터, 조회 실패 여부, 연결한 프로젝트 |
| 과거 차트가 비어 있음 | `candles` 날짜·거래소, 수집 로그, DB 조회 오류 |
| 오늘 시세만 안 나옴 | 브라우저 Network의 `/api/stock/today/...` 응답, 외부 자료 날짜 |
| 기업정보에 `-`가 많음 | 재무·기업정보 수집과 마이그레이션, API 응답의 null 값 |
| 별·메모가 새로고침 후 사라짐 | 저장 요청 오류, 로그인 여부, 브라우저 저장소, DB 정책 |
| Google 로그인 후 잘못된 주소로 이동 | Supabase 허용 복귀 주소, 현재 접속 주소, `/auth/callback` |
| 토론 등록은 되지만 즉시 보이지 않음 | DB 저장 결과와 Realtime 구독·publication을 나눠 확인 |
| 랭킹이 비거나 숫자가 오래됨 | view 적용 여부, 원본 일봉·재무 자료 날짜 |
| 뉴스 탭에 준비 중 표시 | 현재 의도된 미구현 안내 |

브라우저 개발자 도구의 **Console**은 브라우저 오류, **Network**는 요청과 응답을 봅니다. 서버 오류는 `npm run dev`를 켠 터미널, 자동 수집 오류는 GitHub Actions 로그에서 찾습니다. Network의 400은 요청 형식, 401/403은 인증·권한, 500은 서버 처리 문제를 의심할 단서입니다. 최종 원인은 응답 본문과 서버 로그를 함께 봅니다.

## 기존 설명과 달랐던 점

| 예전 설명 또는 흔적 | 현재 소스에서 확인한 상태 |
|---|---|
| 홈은 검색 안내 페이지 | 관심 종목 가격과 토론 피드 |
| 현재가 미구현 | 네이버 조회 API와 폴링 있음 |
| 재무 수집 수동 전용 | 월요일 예약과 수동 실행 모두 있음 |
| 모든 조회가 Query의 5분 캐시 사용 | Provider만 준비되어 있고 현재 조회는 주로 직접 구현 |
| 메모는 DB에서 본인만 접근 | 후속 SQL에서 공개 정책으로 변경됨. 운영 적용 상태는 별도 확인 |
| 무료 메모 종목당 5개 | 설명 흔적은 있으나 현재 저장 핸들러에서 개수 제한을 확인하지 못함 |
| 월/연 결제 가격표 | 실제 Stripe 결제·구독 흐름은 확인되지 않음 |
| 도배 방지 쿨다운 | AGENTS.md의 검토 지침을 구현 완료로 해석하면 안 됨 |

이번 문서 작성에서는 이런 차이를 설명했으며 앱 동작이나 DB 정책을 수정하지 않았습니다.
