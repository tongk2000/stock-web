# 6. 작은 수정으로 직접 이해하기

[목차](README.md) · [이전](05-running.md)

이 실습은 설명을 위한 제안입니다. 현재 소스에는 아래 실습 변경을 적용하지 않았습니다. 개발 서버를 켜고 한 가지씩 수정해 보세요.

## 준비: 수정 전 상태 확인하기

실제 앱 폴더에서 실행합니다.

```sh
git status --short
```

**Git**은 파일 변경 이력을 관리하는 도구입니다. 이 명령은 바뀐 파일 목록을 보여줍니다. 이미 바뀐 파일이 있으면 자신이나 AI가 작업 중인 내용일 수 있습니다. 실습을 되돌릴 때 기존 변경까지 지우지 않도록 수정 전 내용을 확인해 둡니다.

## 실습 1: 홈 제목을 내 말로 바꾸기

1. [src/app/page.tsx](../src/app/page.tsx)를 엽니다.
2. `내 관심 종목`이라는 글자를 찾습니다.
3. 그 글자만 `내가 지켜보는 종목`으로 바꾸고 저장합니다.
4. 브라우저 홈에서 새 제목을 확인합니다.
5. 편집기에서 방금 변경만 되돌리고 저장해 원래 제목도 확인합니다.

배우는 것: `page.tsx`가 그 주소의 본문이며, 태그 사이 글자가 화면 문구입니다. DB나 로그인 코드를 바꾸지 않고도 화면을 수정할 수 있습니다.

## 실습 2: 종목 페이지에서 먼저 보이는 탭 바꾸기

[StockDetailTabs.tsx](../src/components/stock/StockDetailTabs.tsx)에서 다음 줄을 찾습니다.

```tsx
const [active, setActive] = useState<TabId>('discussion');
```

마지막 `'discussion'`만 `'info'`로 바꿉니다. 저장한 뒤 종목 상세를 새로 열거나 새로고침합니다. 기업정보 탭이 먼저 보이고 토론방을 클릭하면 전환되는지 확인합니다. 개발 중에는 상태를 유지하는 갱신 때문에 첫 기본값 변경이 바로 보이지 않을 수 있으므로 새로고침도 해보세요.

배우는 것: state의 초기값은 첫 화면 선택을 결정합니다. `TABS`의 `label`은 보이는 글자이고 `id`는 코드에서 구별하는 값입니다. `info`를 임의로 `기업정보`로 바꾸면 타입과 조건식이 맞지 않을 수 있습니다.

## 실습 3: 여백을 바꾸며 CSS 이해하기

[홈](../src/app/page.tsx)의 `<main>`에는 `px-2`, `py-6`, `sm:px-6`, `sm:py-8`이 있습니다.

| 표현 | 의미 |
|---|---|
| `p` | 안쪽 여백 |
| `px` / `py` | 가로 / 세로 안쪽 여백 |
| `text-2xl` | 글자 크기 |
| `font-bold` | 굵은 글자 |
| `flex` | 자식 요소를 유연하게 나란히 배치 |
| `sm:` | 일정 너비 이상에서만 적용하는 조건 |
| `dark:` | 다크 모드에서 적용하는 조건 |

`py-6`을 `py-8`로 바꿔 좁은 화면의 위아래 여백을 비교해 봅니다. 넓은 화면에서는 이미 `sm:py-8`이 적용되어 차이가 안 보일 수 있습니다. 숫자 8은 8px이라는 뜻이 아니라 Tailwind의 간격 단위입니다.

배우는 것: 같은 코드도 화면 너비에 따라 모양이 달라집니다. 데스크톱에서만 확인하면 모바일 변경을 놓칠 수 있습니다.

## 실습 4: 코드 수정 없이 데이터의 여행 관찰하기

1. 브라우저 개발자 도구에서 Network를 열어 둡니다.
2. DB에 있는 종목 상세로 이동합니다.
3. `today`로 필터링해 `/api/stock/today/종목코드`를 찾습니다.
4. 응답에서 `date`, `open`, `high`, `low`, `close`, `volume`을 봅니다.
5. 기업정보 탭을 눌러 `company-info` 요청이 생기는지 봅니다.
6. Supabase 도메인으로 직접 나가는 요청도 찾아봅니다.

장외에도 첫 조회는 시도할 수 있고, 외부 상태에 따라 오늘 자료가 없거나 오류가 날 수 있습니다. 응답 값과 화면 값이 연결되는지 관찰하는 실습입니다. 토큰·쿠키·키를 복사해 공유할 필요는 없습니다.

배우는 것: 모든 요청이 우리 `/api`를 거치는 것은 아닙니다. 브라우저가 Supabase와 직접 통신하는 부분도 있습니다.

## 바꾼 뒤 검증하는 습관

터미널의 실제 앱 폴더에서 다음을 실행합니다. 개발 서버는 다른 패널에서 계속 실행해도 됩니다.

```sh
git diff
npm run lint
npm run build
```

`git diff`는 수정 전후의 차이를 보여줍니다. 의도하지 않은 파일까지 바뀌었는지 봅니다. lint와 build에서 오류가 나면 오류 위치와 수정한 파일을 비교합니다. 기존 오류인지 새 변경으로 생긴 오류인지 구분해야 합니다.

| 바꾼 내용 | 직접 확인할 행동 |
|---|---|
| 글자·여백 | 해당 페이지를 좁은 화면·넓은 화면에서 보기 |
| 탭 | 기본 선택, 다른 탭으로 이동, 새로고침 |
| 즐겨찾기 | 로그인 전·후 추가/삭제, 홈 이동, 새로고침 |
| 차트 | 종목 이동, 일·주·월봉, 과거 자료와 오늘 자료 |
| 저장 로직 | 저장 직후와 새로고침 뒤 결과, 실패 응답 |

빌드 성공은 코드가 배포용으로 만들어졌다는 증거입니다. DB에 저장되는지, 모바일 버튼이 가려지는지까지 보장하지 않습니다.

## AI에게 맡길 때 요청문도 구체적으로

처음에는 큰 파일 전체를 이해하지 못해도 괜찮습니다. 대상 파일과 기대 행동, 확인 방법을 함께 주면 결과를 판단하기 쉬워집니다.

**이해를 더 돕는 요청 예시**

> `src/components/stock/FavoriteButton.tsx`와 `src/contexts/FavoritesContext.tsx`를 읽고, 별을 누른 순간부터 저장까지 순서대로 설명해 줘. React 초보 기준으로 용어를 처음 쓸 때 설명하고, 비로그인과 로그인 흐름을 구분해 줘. 설명과 실제 코드가 다른 부분이 있으면 표시해 줘.

**작은 수정 요청 예시**

> 홈 제목을 “내가 지켜보는 종목”으로 바꿔 줘. `src/app/page.tsx`의 제목 문구가 대상이야. 수정 파일과 바뀐 부분을 설명하고, 기존 기능에 영향을 주는 변경이 있는지도 알려 줘.

**저장 오류 개선 요청 예시**

> 로그인 상태에서 즐겨찾기 저장이 실패해도 별이 바뀌어 보이는 문제를 고쳐 줘. FavoritesContext의 추가/삭제 흐름을 확인하고, 실패 시 안내와 상태 복구를 구현해 줘. 성공·실패·새로고침 후 동작을 어떻게 검증했는지 알려 주고 관련 설명서도 갱신해 줘.

**오류 보고 양식**

```text
내가 하려던 일:
문제가 난 주소:
재현 순서: 1. ... 2. ... 3. ...
기대한 결과:
실제 결과:
로그인 여부:
브라우저 / 화면 너비:
최근 수정 파일:
터미널 또는 Console 오류: (비밀 값은 제거)
실패한 Network 요청 경로와 상태 코드: (토큰·쿠키는 제거)
```

“안 돼”보다 “로그인 뒤 별을 누르면 노랗게 바뀌지만 새로고침하면 사라진다”가 원인을 훨씬 좁혀줍니다.

## 다음부터 혼자 읽는 순서

원하는 화면 주소를 찾고, [파일 지도](03-file-map.md)에서 `page.tsx`를 엽니다. 화면 태그 중 대문자로 시작하는 컴포넌트를 따라갑니다. `onClick`, `onSubmit` 같은 행동을 찾고, 그 함수 안의 `set...`, `fetch`, `supabase.from(...)`을 확인합니다. 마지막으로 저장되는 표와 권한을 봅니다.

이 순서가 익숙해지면 AI가 만든 코드도 “거대한 한 덩어리”가 아니라 **화면 → 동작 → 요청 → 저장**의 연결로 읽을 수 있습니다.
